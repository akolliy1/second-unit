Overview

A summary page, deliberately. It answers two questions — what needs a human, and what is the state of the platform — and links to the page that owns each detail. It does not list the farm: /shots does that, with paging, filters and sorting built for it.

Why the lists are capped

This page previously rendered every shot in /api/fleet. At 63 in-flight passes that was roughly 5,400px of scroll, almost all of it healthy rows, and it made the one thing that needed attention harder to find rather than easier. Caps here are a correctness property, not a layout preference:

  • Attention — at most 5 exception rows, worst first, plus at most 3 unmeasurable ones. Anything beyond that becomes "+N more →".
  • Departments — one stacked bar and its legend; six departments, not six hundred rows.
  • Everything else — a count and a link. No section grows with the farm.

Every capped list prints what it is hiding and links to the full view. A cap that does not say what it dropped is a lie by omission, and the count comes from the API's own total rather than from the rows we chose to draw.

Attention

GET /api/fleet, every 20s. The sweep is plain Python over two instant queries — shot_frames_remaining and sum by (shot) (rate(render_frames_completed_total[15m])) * 60 — then division: frames ÷ rate gives an ETA, and the ETA minus the published review deadline gives the slip. No language model is in that path, so this section cannot hallucinate a shot, invent an ETA, or disagree with itself between refreshes. The server already sorts worst-first, so the cap takes the five worst rather than the first five it happened to receive.

  • critical — forecast more than 1h past the deadline
  • at risk — forecast past the deadline at all
  • unknown — frames remain but the rate is unusable: nothing completed in the last 15m, or an implausible rate from a counter reset. Shown with its note, never folded into "on track" and never hidden.
  • on track / done — counted in the all-clear line, not listed. Their detail lives on /shots?tab=forecast.

An empty section is never rendered as calm. A failed sweep prints fleet.last_error; a sweep that succeeded and returned nothing says so and explains that for this farm it means shot_frames_remaining has no series, i.e. the seeder stopped. When there are genuinely no exceptions, the all-clear states how many shots are being watched and when the next fault lands — a calm farm must not look like a broken page.

If the review deadline could not be read from shot_review_deadline_seconds, the API says so via deadline_is_placeholder and a warning appears above everything else. Every ETA and slip on the page is then measured against a made-up deadline and none of them are schedule facts.

Active incident

The worst exception from the same /api/fleet payload — no second data source, so the card and the attention list cannot contradict each other. All three framings are rendered once and selected in CSS from html[data-persona]: a Producer gets the schedule consequence in plain language and no metric names, a Supervisor gets the shot and the cause, a Pipeline TD gets nodes, rates and the exact queries. The finding underneath is identical; only the wording differs.

Platform at a glance

Four tiles, each with its source printed on it:

  • Slate — GET /api/shots → summary: total, ingested_today, and by_state (rendering vs complete). The catalogue, not Prometheus — it is hundreds of shots and grows daily.
  • Farm — GET /api/fleet for the number of shots with live telemetry, then GET /api/vitals for sum(rate(render_frames_completed_total[15m])) * 60, sum by (node) (increase(render_node_gpu_ecc_errors_total[30m])) > 0 and render_queue_depth{queue="lighting"} (~18 is this farm's healthy depth; 40+ means frames are piling up faster than the pool clears them).
  • Departments — GET /api/shots/facets → department, drawn as a stacked bar of divs. No chart library: six proportions do not justify a dependency, and a div cannot fail to load.
  • Agent — GET /api/agent/metrics: tool_calls summed across stages, and the write_claims breakdown.

The write-claim outcomes are read back out of the same Prometheus the farm writes to — not from memory in this process — so these are the numbers in Grafana and the page cannot flatter the agent:

  • confirmed — the agent claimed a write and verification found it in the stack
  • honest failure — the write failed and the agent said it failed
  • unchecked — no independent check was possible for that item
  • false success — the agent reported a write that verification could not find. The one number worth paging on, so a non-zero value gets a banner above the tiles as well as the tile treatment.

These are instant queries. If the agent has not run inside Prometheus's retention window the series are empty, and the tile says "no run in the window" rather than showing zeroes — zero false successes and no data are not the same claim.

Scenario state

Cycle phase is derived from the deadline metric, not from a wall clock: the demo farm replays a ~4h incident loop. During repaired, restarting and pre-fault the farm is genuinely healthy, and this section says when the next fault is injected. It exists so a judge arriving mid-repair is not left concluding the product is broken.

Freshness and polling

/api/fleet and /api/vitals refresh every 20 seconds and no faster; each hits Prometheus through Grafana's datasource proxy. The slate, facets and agent summaries refresh every 60s — the catalogue changes once a day and the agent's numbers only when a run happens. Polling pauses while the tab is hidden and resumes on return. A section is only rewritten when its rendered output actually changed, so a poll cannot reflow the page under the reader's cursor. The dot in the top bar is green after a clean sweep, amber when something is degraded or a deadline is a placeholder, and red when a call failed — with the reason on the page, never only in the console.
