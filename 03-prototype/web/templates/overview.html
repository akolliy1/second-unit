    Overview

    The triage view: every shot in flight, the one exception in your own language, the farm's current vitals, and whether the agent's last run told the truth about what it wrote.

    Fleet triage strip

    GET /api/fleet. Each row is one shot with a live series in Prometheus. The sweep is plain Python over two instant queries — shot_frames_remaining and sum by (shot) (rate(render_frames_completed_total[15m])) * 60 — then division: frames ÷ rate gives an ETA, and the ETA minus the published review deadline gives the slip. No language model is in that path, so the strip cannot hallucinate a shot, invent an ETA, or disagree with itself between refreshes.

    • critical — forecast more than 1h past the deadline
    • at risk — forecast past the deadline at all
    • on track — forecast to land before it
    • done — zero frames remaining on that pass
    • unknown — frames remain but nothing completed in the last 15m: stalled, or the metric stopped arriving. Deliberately not called "on track".

    An empty strip is never rendered as calm. If the sweep failed, the reason from fleet.last_error is printed here instead; if it succeeded and returned nothing, that is stated as "no shots in flight" — which for this farm most likely means the seeder stopped.

    If the review deadline could not be read from shot_review_deadline_seconds, the API says so via deadline_is_placeholder and a warning appears above the strip. Every ETA and slip on this page is then measured against a made-up deadline and none of them are schedule facts.

    Active incident

    The worst exception from the same /api/fleet payload — no second data source, so the card and the strip cannot contradict each other. The wording changes with the persona in the top bar: a Producer gets the schedule consequence and no PromQL, a Supervisor gets the shot and the cause, a Pipeline TD gets nodes, rates and the exact queries. The finding underneath is identical; only the framing differs.

    When no shot is an exception, the card says so and explains where the looping scenario currently is, rather than showing an empty box.

    Farm vitals

    GET /api/vitals, one instant query per number:

    • Throughput — sum(rate(render_frames_completed_total[15m])) * 60
    • Lighting queue — render_queue_depth{queue="lighting"}; ~18 is this farm's healthy depth
    • Nodes with faults — sum by (node) (increase(render_node_gpu_ecc_errors_total[30m])) > 0. Uncorrectable ECC is the injected fault, so an empty list here is a real signal
    • Hottest GPU — topk(1, render_node_gpu_temp_celsius); context, not an alert

    Cycle phase is derived from the deadline metric, not from a wall clock: the demo farm replays a ~4h incident loop. During repaired, restarting and pre-fault the farm is genuinely healthy and the banner says when the next fault lands. A calm farm mid-loop is the scenario working, not the product failing.

    Agent health

    GET /api/agent/metrics, read back out of the same Prometheus the farm writes to — not from memory in this process — so these numbers are the ones in Grafana and this page cannot flatter the agent.

    • confirmed — the agent claimed a write and verification found it in the stack
    • honest failure — the write failed and the agent said it failed
    • unchecked — no independent check was possible for that item
    • false success — the agent reported a write that verification could not find. The one number worth paging on.

    These are instant queries. If the agent has not run inside Prometheus's retention window the series are empty, and this section says "no run in the window" rather than showing zeroes — zero false successes and no data are not the same claim.

    Freshness and polling

    The fleet and vitals calls run every 20 seconds and no faster; each one hits Prometheus through Grafana's datasource proxy. Agent metrics refresh every 60s. Polling pauses while the tab is hidden and resumes on return. The dot in the top bar is green after a clean sweep, amber when something is degraded or a deadline is a placeholder, and red when a call failed — with the reason on the page, never only in the console.
