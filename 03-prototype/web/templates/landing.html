Your render farm already knows which shot misses Friday. Nobody who needs that can read it.

Second Unit is an autonomous post-production pipeline SRE. A crew of Gemini agents reads a VFX render farm's telemetry through the Grafana MCP server, works out which shot is going to miss its client review and by how long, and, only after a human approves, writes the incident back into Grafana.

Why this exists

A visual effects house lives and dies by the client review date.

The data was never missing. What's missing is the translation layer between infrastructure telemetry and production decisions.

The telemetry is already in Grafana

Queue depth, frame rates, GPU errors, and the review deadline itself, all of it is already being scraped. Nothing is missing.

Nobody who needs it can read it

The VFX supervisor doesn't open dashboards. The producer doesn't write PromQL. The answer exists in a language its audience doesn't speak.

The delay is where money burns

A coordinator notices a queue looks slow, asks a pipeline TD, and four hours later somebody says "we're going to miss Friday."

How it works

Five stages, deterministically sequenced, with a typed object at every boundary.

Each stage gets its own model tier and its own tool budget, which of the bridge's 76 tools it may touch. The planner proposes the write-back and holds no write tools at all.

  1. STAGE 1

    Watchtower

    What is abnormal right now, breadth, not diagnosis.

    Gemini Flash
  2. STAGE 2

    Diagnostician

    Why, including what it ruled out, and on what evidence.

    Gemini Pro
  3. STAGE 3

    Impact Forecaster

    The production consequence, in a producer's language.

    Gemini Pro
  4. STAGE 4

    Remediation Planner

    The real-world fix and the proposed write-back. Holds no write tools.

    Gemini Flash
  5. STAGE 5

    Remediation Executor

    Performs approved writes, one agent call per write.

    Gemini Flash

The model decides what it finds. Code decides what happens next.

Every guarantee I tried to express as an instruction held most of the time, which is worse than failing, because it passes testing. Nothing is written without human approval because the planning stage has no mutating tools and the executor is constructed only from an approval record. The delivery forecast is arithmetic, and it refuses implausible input rather than forecasting from it.

The fleet sweep behind the numbers above uses no model at all, plain Python over one Prometheus query, every shot every time, so it cannot hallucinate a shot and costs nothing to refresh. The agent is spent only on the exception.

Verification

The agent's report is a claim. The system checks it, out of band, and shows the disagreement.

After an approved write-back, verify.py diffs the stack through Grafana's HTTP API, not the MCP tools the agent just used, and prints what it finds. A verifier that asks the same tool that just lied learns nothing.

confirmed …

Present in the stack, exactly as reported.

honest_failure …

Reported as failed, and it genuinely failed. Trustworthy.

unchecked …

No out-of-band check was possible. Said so rather than assumed.

false_success …

Reported successful, but not present in the stack.

That last outcome is not hypothetical. It is why the module exists, I watched an agent report a write it had not made. So the outcome is a metric, graphable next to everything else, and visible on the Agent page of the console:

second_unit_write_claims_total{outcome="false_success"}

Counts are the last recorded values from its own observability series, read back from Prometheus.

Built on

Imported and called at runtime, not named in a README.

Google Cloud
  • Vertex AI. Gemini 2.5 Flash and Pro behind all five stages
  • Agent Development Kit, five LlmAgents with an output schema on every boundary
  • Cloud Run, service plus a job for the telemetry seeder, and a Scheduler trigger
  • Secret Manager, every credential; nothing in an image
  • Cloud Text-to-Speech. Chirp3-HD, for the spoken dailies briefing
Grafana
  • Grafana Cloud MCP, the bridge exposes 76 tools; every fact the agent states comes through them
  • Prometheus and Loki, queried live, read and written
  • Agent Observability, the agent's own tokens, latencies and failures pushed to the same stack it investigates
  • Dashboards and annotations, the approved write-back lands where the crew already looks

Twenty of those 76 tools are wired into the five stage budgets, read tools for the first four stages, write tools handed out only after a human approves.

Those twenty tools are: list_datasources, list_alert_groups, list_prometheus_metric_names, list_prometheus_label_values, query_prometheus, list_loki_label_names, list_loki_label_values, query_loki_logs, query_loki_patterns, analyze_loki_labels, check_datasources_health, search_folders, search_dashboards, get_dashboard_summary, get_dashboard_by_uid, generate_deeplink, create_folder, create_annotation, update_dashboard, alerting_manage_rules.
