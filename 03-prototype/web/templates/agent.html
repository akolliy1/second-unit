Write-claim verification · the agent's self-report, checked

Counted by second_unit_write_claims_total{outcome}, written by observe.py after every approved write-back. The check itself is verify.py: a before/after diff of the Grafana stack over its HTTP API — /api/search, /api/annotations, /api/v1/provisioning/alert-rules — deliberately not the MCP tools the agent just used. The model decides what to do; code decides what is true.

No verification samples in the query window — this is not "zero false successes".

/api/agent/metrics asks Prometheus for instant values, and an instant query only sees samples from roughly the last five minutes. If the most recent investigation pushed its telemetry before that, every series here reads empty. Empty means unobserved. Reporting it as a clean sheet would be exactly the laundering this panel exists to prevent — run an investigation, or read the series over a longer range in Grafana (link at the bottom of this page).

    Agent — observed

    Our own agent's telemetry, read back from the stack it writes to. The page is here to make the agent falsifiable: it reports what an investigation cost, what failed, and whether the writes it claimed actually happened.

    The self-report is a claim

    An agent that says "annotation created" has produced a sentence, not a result. In a real run the executor reported four dashboard writes and created no dashboard at all; reading its own report you would have concluded three writes landed. One did. That run is why second_unit_write_claims_total exists.

    Verification is out of band

    • verify.py snapshots the stack before the write-back — dashboard UIDs, annotation ids, alert-rule UIDs — then diffs it after.
    • It reads Grafana's own HTTP API (/api/search, /api/annotations, /api/v1/provisioning/alert-rules), not the MCP tools the agent used. A verifier that asks the same tool that just lied learns nothing.
    • A claim is credited only when a new object of the right kind appeared. Matching by name was tried first and produced false confirmations, because a built-in Grafana dashboard happened to contain a matching word. An id diff has no false-positive mode.

    The four outcomes

    • confirmed — claimed success, new object found.
    • honest_failure — reported failure, and nothing appeared. The agent was right about the world; trust is intact.
    • unchecked — an action type with no independent check implemented. Counted, not credited.
    • false_success — claimed success, nothing found. The one number worth paging on. It is drawn hatched red and given the top of the page whenever it is above zero.

    Where the numbers come from

    • second_unit_run_seconds{stage} — wall clock per stage, plus a stage="total" series for the run, shown separately rather than as a row.
    • second_unit_tool_calls_total{stage} — MCP calls per stage.
    • second_unit_tokens_total{stage,kind} — prompt and candidate tokens per stage.
    • second_unit_tool_latency_ms{stage,tool} — per-call round trip, measured around the call in the agent.
    • second_unit_stage_failures_total{stage,reason} — bucketed to four reasons so the label cardinality stays bounded.

    Why the page cannot flatter the agent

    These metrics are not kept in the web process. They are pushed to Prometheus by the agent (observe.py, batched once per run so measuring latency does not add latency) and read back by /api/agent/metrics through Grafana's datasource proxy. The page and a Grafana dashboard are reading the same samples, so a number here that nobody can reproduce in Explore is a bug in this page, not a favourable reading.

    Instant queries have a ~5 minute lookback, so a run older than that leaves every panel empty. Empty is rendered as unobserved, never as zero — particularly for false_success, where "no data" and "none" are opposite claims.

    Cost, and why two model tiers

    Tool-using stages spend most of their tokens on telemetry pulled into context rather than on generated text — the prompt:candidate ratio in the panel is the evidence. Retrieval work that is mostly "fetch and summarise" runs on the cheaper Flash model (GEMINI_MODEL); the two stages whose output people plan around — the diagnosis and the impact forecast — get the stronger model (GEMINI_MODEL_STRONG). The tier shown per row is the default in stages.py; the diagnostician accepts an override because the strong model is also the first to hit a quota, and a degraded-but-answering diagnosis beats a 429.
