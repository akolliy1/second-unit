    Agent — observed

    Our own agent's telemetry, read back from the stack it writes to. The page is here to make the agent falsifiable: it reports what an investigation cost, what failed, and whether the writes it claimed actually happened.

    What is pinned, and why

    Two things sit above the tabs and are never hidden by a tab choice:

    • the plain-language verdict — the same payload, translated for a reader whose question is "can I act on this?" rather than "what did it cost?" (shown to supervisor and producer);
    • the write-claim verification headline — confirmed, honest_failure, unchecked, false_success.

    The tabs hold cost, latency, failures and the Grafana link-out. That split is the argument of the page: everything in a tab is accounting, and the pinned block is the only part that says whether the agent's self-report was true. A false_success above zero is forced visible for every persona — it is not something a view setting gets to suppress.

    The self-report is a claim

    An agent that says "annotation created" has produced a sentence, not a result. In a real run the executor reported four dashboard writes and created no dashboard at all; reading its own report you would have concluded three writes landed. One did. That run is why second_unit_write_claims_total exists.

    Verification is out of band

    • verify.py snapshots the stack before the write-back — dashboard UIDs, annotation ids, alert-rule UIDs — then diffs it after.
    • It reads Grafana's own HTTP API (/api/search, /api/annotations, /api/v1/provisioning/alert-rules), not the MCP tools the agent used. A verifier that asks the same tool that just lied learns nothing.
    • A claim is credited only when a new object of the right kind appeared. Matching by name was tried first and produced false confirmations, because a built-in Grafana dashboard happened to contain a matching word. An id diff has no false-positive mode.

    The four outcomes

    • confirmed — claimed success, new object found.
    • honest_failure — reported failure, and nothing appeared. The agent was right about the world; trust is intact.
    • unchecked — an action type with no independent check implemented. Counted, not credited.
    • false_success — claimed success, nothing found. The one number worth paging on. It is drawn hatched red and given the top of the page whenever it is above zero.

    Where each number comes from

    All of it from one request — GET /api/agent/metrics — read back out of Prometheus, never held in the web process's memory. Per tab:

    • pinned headline — second_unit_write_claims_total{outcome}.
    • Cost — second_unit_run_seconds{stage} for wall clock (plus a stage="total" series for the run, shown in the legend rather than as a row), second_unit_tool_calls_total{stage} for MCP calls, and second_unit_tokens_total{stage,kind} for prompt and candidate tokens.
    • Latency — second_unit_tool_latency_ms{stage,tool}, per-call round trip measured around the call in the agent, slowest first.
    • Failures — second_unit_stage_failures_total{stage,reason}, bucketed to four reasons so the label cardinality stays bounded.
    • Grafana — GRAFANA_URL from the server, stack root only.

    The count pill on each tab is computed from that same payload: stages observed, tool round trips measured, failures recorded. A pill reading – means the series was absent, not zero.

    Why the page cannot flatter the agent

    These metrics are not kept in the web process. They are pushed to Prometheus by the agent (observe.py, batched once per run so measuring latency does not add latency) and read back by /api/agent/metrics through Grafana's datasource proxy. The page and a Grafana dashboard are reading the same samples, so a number here that nobody can reproduce in Explore is a bug in this page, not a favourable reading.

    These series are written once per investigation, so the endpoint asks for last_over_time over a window (window in the response, named in every tab note) rather than an instant value. A run older than that window leaves every panel empty. Empty is rendered as unobserved, never as zero — particularly for false_success, where "no data" and "none" are opposite claims.

    Cost, and why two model tiers

    Tool-using stages spend most of their tokens on telemetry pulled into context rather than on generated text — the prompt:candidate ratio in the Cost tab is the evidence. Retrieval work that is mostly "fetch and summarise" runs on the cheaper Flash model (GEMINI_MODEL); the two stages whose output people plan around — the diagnosis and the impact forecast — get the stronger model (GEMINI_MODEL_STRONG). The tier shown per row is the default in stages.py; the diagnostician accepts an override because the strong model is also the first to hit a quota, and a degraded-but-answering diagnosis beats a 429.
